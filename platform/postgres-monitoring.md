# Мониторинг PostgreSQL

## Что собирает данные

| Компонент | Что хранит | Что отвечает |
|---|---|---|
| **Prometheus** | Числовые временные ряды | Состояние экземпляра: подключения, активность запросов, ресурсы, рестарты |
| **Loki** | Текстовые логи | Сообщения PostgreSQL: ошибки, предупреждения, сведения о запросах |

Логи PostgreSQL пишутся в структурированном виде (JSON), поэтому по ним можно фильтровать
не только по тексту, но и по полям: уровню сообщения, коду состояния, типу процесса.

Диагностические данные доступны по идентификатору экземпляра из обращения. Платформа
сопоставляет его с временными рядами и потоками логов по своим соглашениям — отдельная
инвентаризация баз не требуется.

## Как читать метрики

### 1. Активные подключения и `max_connections`

Сравнивать нужно **две величины**: текущее число подключений и настроенный лимит. По отдельности
они не значат ничего.

| Ситуация | Как трактовать |
|---|---|
| Подключений мало, лимит высокий | Нет давления по подключениям |
| Подключений близко к лимиту | Риск отказов новых подключений, нужен разбор пула на стороне приложения |
| Подключений больше, чем активных запросов | Соединения простаивают — вероятно, проблема в пуле, а не в нагрузке |

Важно различать: **число подключений приложения** и **число подключений на стороне
PostgreSQL** — это не одно и то же. Один экземпляр приложения с пулом на N соединений
и десять реплик с тем же пулом дадут разное число соединений в базе.

### 2. Длительность выполнения запросов

Показывает, насколько долго выполняется самый продолжительный активный запрос. Рост этой
величины означает деградацию, но не говорит о причине: это может быть тяжёлый запрос,
ожидание блокировки или нехватка ресурсов.

Долгий запрос и **ожидание блокировки** различаются: в первом случае запрос работает,
во втором — стоит и ждёт освобождения ресурса. Метрики длительности их не разделяют,
поэтому нужны логи.

### 3. Использование CPU

Высокая утилизация CPU **не всегда означает проблему**. Признаком инцидента она становится,
когда:

- утилизация устойчиво держится на пределе выделенного ресурса, а не кратковременно
  подскакивает во время плановой операции;
- одновременно растёт длительность запросов;
- в логах есть конкретные запросы, которые можно показать дежурному.

Кратковременный рост CPU при загрузке данных или миграции — нормальное поведение.

### 4. Использование памяти

Рост потребления памяти опасен в первую очередь приближением к лимиту: при его достижении
контейнер будет принудительно завершён, и это уже авария, а не деградация.

Полезно смотреть не только на объём, но и на эффективность кэша: если кэш перестал
попадать, значит рабочий набор данных вырос, и дальше будут обращения к диску.

### 5. Рестарты PostgreSQL

Признаком рестарта служит сброс накопленных счётчиков и изменение времени запуска процесса.
Рестарт **не всегда является причиной проблемы** — он может быть следствием: нехватки памяти,
принудительного завершения, платформенного вмешательства. Вывод «база перезапустилась, значит
виновата платформа» делать нельзя.

### 6. Ошибки подключения

Смотреть в логах по уровню сообщения и по тексту: отказ в подключении, отказ по правам,
исчерпание слотов. Ошибки подключения могут возникать на стороне приложения, а не базы.

### 7. Состояние PostgreSQL

Отдельно проверяется, отвечает ли сама база и работает ли сборщик метрик. Если сборщик
перестал отдавать данные, это не значит, что база недоступна — это значит, что метрики
недостоверны, и диагноз по ним строить нельзя.

## Ограничения мониторинга

- **Отсутствие метрик не доказывает отсутствие проблемы.** Пропажа данных может означать,
  что перестал работать экспортер, а база при этом жива.
- **Свободное место на хранилище в Prometheus не отображается.** Оценить скорость роста
  можно, абсолютный остаток — нет.
- **Набор метрик зависит от экспортера и конфигурации платформы.** Имена и состав показателей
  могут отличаться от привычных по другим инсталляциям PostgreSQL. Перед использованием
  конкретной метрики нужно убедиться, что она есть в системе.
- **В метриках нет идентификаторов сессий.** Метрики агрегированы по экземпляру: они не
  содержат PID процесса, текста запроса и плана выполнения.

## Идентификаторы сессий в логах

То, чего нет в метриках, присутствует в логах. Каждая запись содержит поля:

| Поле | Смысл |
|---|---|
| `record_process_id` | **PID процесса PostgreSQL**, обслуживающего сессию |
| `record_session_id` | Идентификатор сессии в формате `<PID в hex>.<счётчик>` |
| `record_backend_type` | Тип процесса: `client backend`, `checkpointer`, `walwriter`, `autovacuum worker` |
| `record_sql_state_code` | Код SQLSTATE |
| `record_error_severity` | `LOG`, `WARNING`, `ERROR`, `FATAL` |

Это позволяет связать сообщение из лога с конкретным процессом и передать пользователю PID,
не имея доступа к его базе.

Важно: **не все события попадают в лог.** Сообщения о длительности запросов пишутся только
если на экземпляре включён параметр `log_min_duration_statement`. При выключенном значении
успешно выполненный долгий запрос в логе не отражается — фиксируются только ошибки
и отмены.

## Соответствие категорий и метрик

Актуальный набор метрик, подтверждённый конфигурацией мониторинга платформы:

| Категория | Метрики |
|---|---|
| Подключения | `cnpg_backends_total`, `cnpg_backends_waiting_total`, `cnpg_pg_settings_setting` (значение `max_connections` — в метрике, имя настройки — в лейбле `name`) |
| Длительность запросов | `cnpg_backends_max_tx_duration_seconds`, `cnpg_pg_stat_database_blk_read_time`, `cnpg_pg_stat_database_blk_write_time`, `cnpg_pg_stat_database_temp_bytes` |
| Активность запросов | `cnpg_pg_stat_database_xact_commit`, `cnpg_pg_stat_database_xact_rollback`, `cnpg_pg_stat_database_tup_fetched`, `cnpg_pg_stat_database_tup_returned`, `cnpg_pg_stat_database_deadlocks` |
| CPU и память | `container_cpu_usage_seconds_total`, `container_memory_working_set_bytes`, `cnpg_pg_stat_bgwriter_buffers_clean`, `cnpg_cache_hits`, `cnpg_cache_miss` |
| Рестарты и состояние | `cnpg_pg_postmaster_start_time`, `cnpg_collector_up`, `cnpg_collector_last_collection_error` |
| Проблемы хранилища | `cnpg_collector_pg_wal`, `cnpg_collector_pg_wal_archive_status`, `cnpg_pg_database_xid_age` |

Имена метрик специфичны для экспортёра платформы. Для остальных инсталляций PostgreSQL состав
будет другим — опираться на эту таблицу вне платформы нельзя.
