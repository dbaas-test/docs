# Runbook: база данных недоступна

**Когда использовать этот документ**

Обращения вида:

- «База данных недоступна»
- «Приложение не может подключиться, хотя раньше всё работало»
- «PostgreSQL перезапустился»
- «Connection refused, сервер не принимает подключения»
- «После перезапуска база не вернулась»
- «База периодически отваливается»

**Категория:** `availability`
**Типовой приоритет:** высокий

## Симптомы

Подключение к базе не устанавливается или рвётся. В отличие от
[connection-pool.md](connection-pool.md), здесь ошибка **не самоустраняется**.

## Важно: три ложных вывода

Этот runbook существует в первую очередь для того, чтобы их не сделать.

| Ложный вывод | Почему он неверен |
|---|---|
| «База перезапустилась — значит причина в платформе» | Рестарт может быть **следствием**: исчерпание памяти, платформенное обслуживание, принудительное завершение |
| «Метрик нет — значит база недоступна» | Метрики могут пропасть из-за недоступности **сборщика**, при живой базе |
| «Процесс убит по памяти — это доказано» | Требует фактического подтверждения: признаков рестарта и данных о ресурсах |

**Вывод о причине недоступности нельзя делать по одному симптому.** Если подтверждений
нет — причина остаётся неустановленной.

## Сначала выяснить у пользователя

| Что нужно | Зачем |
|---|---|
| Идентификатор Database Instance | Сопоставить с мониторингом |
| Точное время начала | Отделить платформенные работы от пользовательской проблемы |
| Дословный текст ошибки | Различить отказ в подключении, отказ по правам и таймаут |
| Все приложения затронуты или одно | Отделить платформенную проблему от приложения |
| Есть ли записи, совершённые до сбоя | Оценить риск потери данных |

## Порядок диагностики

### Шаг 1. Проверить, жива ли база и собираются ли метрики

```promql
cnpg_collector_up
cnpg_pg_postmaster_start_time
```

- `cnpg_collector_up = 1` — сборщик метрик отвечает.
- `cnpg_pg_postmaster_start_time` — время старта процесса PostgreSQL.

**Если метрики отсутствуют вообще** — это не доказательство недоступности базы. Нужно
проверить, отвечает ли сборщик, и рассматривать отсутствие данных как ограничение,
а не как факт.

### Шаг 2. Проверить, был ли рестарт

Изменение `cnpg_pg_postmaster_start_time` на более позднее означает, что процесс
перезапускался. Также при рестарте сбрасываются накопленные счётчики.

**Рестарт не является причиной.** Он лишь указывает, что что-то произошло. Причину
нужно подтверждать отдельно.

### Шаг 3. Проверить ресурсы

```promql
container_memory_working_set_bytes{container="postgres"}
rate(container_cpu_usage_seconds_total{container="postgres"}[5m])
```

Потребление памяти у предела даёт основания **предполагать** принудительное завершение,
но не подтверждает его. Подтверждение — признаки рестарта из шага 2 **вместе** с этой метрикой.

### Шаг 4. Проверить ошибки в логах

```logql
{namespace="dbaas", pod="<pod>"} | json | record_error_severity = "FATAL"
{namespace="dbaas", pod="<pod>"} |= "connection refused"
{namespace="dbaas", pod="<pod>"} |= "the database system is starting up"
{namespace="dbaas", pod="<pod>"} |= "out of memory"
```

Сообщение `the database system is starting up` означает, что база поднимается — это
объясняет временную недоступность.

Ошибки платформенного уровня:

```logql
{namespace="dbaas", pod="<pod>"} | json | record_message =~ "archive"
```

### Шаг 5. Проверить, что происходит с соединениями

```promql
cnpg_backends_total
cnpg_backends_waiting_total
```

Резкое падение числа соединений до нуля при живом сборщике — признак того, что база
действительно перестала принимать подключения.

## Возможные причины

| Причина | Чем подтверждается |
|---|---|
| Временная недоступность при старте базы | `the database system is starting up` в логах |
| Рестарт процесса | Изменение `cnpg_pg_postmaster_start_time`, сброс счётчиков |
| Нехватка памяти | Потребление у предела **вместе** с признаками рестарта |
| Ошибки подключения на стороне приложения | Ошибки есть, но база отвечает и метрики идут |
| Проблема платформы | Нет данных от сборщика, нет ответа базы, платформенные сообщения |
| Запланированное обслуживание | Совпадение по времени с окном работ |

## Интерпретация

- **Метрики идут, база отвечает, ошибки только у одного приложения** — проблема
  на стороне приложения, а не платформы.
- **`starting up` в логах, метрики вернулись** — база перезапускалась, доступность
  восстановилась. Причина рестарта требует отдельного подтверждения.
- **Метрик нет, сборщик не отвечает, рестарт не подтверждён** — причина по доступным данным
  **не определяется**. Наблюдения остаются наблюдениями, вывод о причине не делается.
- **Есть признаки рестарта и потребление памяти было у предела** — гипотеза о нехватке
  памяти обоснована, но остаётся гипотезой.

## Что рекомендуется пользователю

- Проверить, что приложение указывает тот же эндпоинт, что и раньше.
- Проверить настройки повторных подключений: временный разрыв не должен приводить
  к остановке приложения.
- Периодически проверять доступность соединения, а не считать его постоянным.
- Если приложение не использует пул, он станет обязательным при дальнейшем росте нагрузки.

## Критерии передачи SRE

- База не отвечает и метрики отсутствуют — требуется платформенная проверка.
- Подтверждён рестарт, причина которого не установлена.
- Недоступность затронула несколько баз или приложений.
- Данных для вывода недостаточно.

## Ограничения

- Прямая проверка подключения к пользовательской базе не выполняется.
- Причина рестарта по метрикам не определяется — нужны логи и платформенные данные.
- Отсутствие метрик нельзя трактовать как недоступность базы.
- Состояние хранилища и платформенных компонентов по доступным метрикам не проверяется.
