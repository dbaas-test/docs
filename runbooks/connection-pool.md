# Runbook: проблемы с подключениями

**Когда использовать этот документ**

Обращения вида:

- «Приложение периодически получает ошибки подключения к PostgreSQL»
- «Иногда подключение восстанавливается самостоятельно»
- «Слишком много подключений»
- «Connection refused, база не принимает соединения»
- «Приложение перестало подключаться после роста числа реплик»
- «Connection pool исчерпан»

**Категория:** `connections`
**Типовой приоритет:** высокий

## Симптомы

Приложение периодически не может установить соединение. Характерная черта: ошибки
**самоустраняются** — через какое-то время подключение проходит снова. Это отличает
исчерпание пула от полной недоступности базы.

Если база недоступна постоянно — смотрите [database-unavailable.md](database-unavailable.md).

## Что нужно понимать до диагностики

Четыре величины, которые часто путают:

| Величина | Что показывает |
|---|---|
| **Соединения приложения** | Сколько соединений открывает приложение (включая все реплики) |
| **Соединения PostgreSQL** | Сколько соединений реально видит база |
| **Лимит подключений** | Сколько соединений база принимает (`max_connections`) |
| **Активные запросы** | Сколько соединений **сейчас** что-то выполняют |

Разница между третьей и четвёртой величинами критична: если соединений много, а активных
запросов мало, значит соединения **простаивают и не освобождаются**. Именно так выглядит
утечка соединений или неверно настроенный пул.

**Большое количество подключений само по себе не означает проблему.** Проблема — это
подключения, которые не освобождаются, либо приближение к лимиту.

## Сначала выяснить у пользователя

| Что нужно | Зачем |
|---|---|
| Идентификатор Database Instance | Сопоставить с мониторингом |
| Когда появились ошибки | Отделить от платформенных изменений |
| Название и число экземпляров приложения | Понять суммарное число соединений |
| Использует ли приложение пул, и какие настройки | Найти причину на стороне клиента |
| Тип ошибки дословно | Различить отказ по слотам и отказ в правах |
| Периодичность ошибок | Оценить, устойчивая это проблема или пиковая |

## Порядок диагностики

### Шаг 1. Проверить, отвечает ли база

Если база недоступна постоянно — смотрите [database-unavailable.md](database-unavailable.md).

### Шаг 2. Сравнить текущее число соединений с лимитом

```promql
cnpg_backends_total
cnpg_pg_settings_setting{name="max_connections"}
```

Особенность метрики настроек: **имя настройки лежит в лейбле `name`, а значение метрики —
это значение настройки.** Отбирать нужно по `name="max_connections"`.

Если `cnpg_backends_total` устойчиво приближается к значению `max_connections` — новые
подключения будут отклоняться. Это уже подтверждённая причина, а не гипотеза.

### Шаг 3. Посмотреть, есть ли ожидающие подключения

```promql
cnpg_backends_waiting_total
```

Подключившиеся, но не получившие обслуживание процессы. Рост значения означает, что клиенты
подключаются, но застревают.

### Шаг 4. Проверить, нагружены ли соединения работой

```promql
rate(cnpg_pg_stat_database_xact_commit[5m])
rate(cnpg_pg_stat_database_xact_rollback[5m])
```

Если соединений много, а транзакций мало — соединения простаивают. Это ключевой признак
утечки соединений или отсутствия корректного пула на стороне приложения.

### Шаг 5. Найти причину в логах

```logql
{namespace="dbaas", pod="<pod>"} |= "too many clients already"
{namespace="dbaas", pod="<pod>"} |= "remaining connection slots"
{namespace="dbaas", pod="<pod>"} |= "sorry, too many clients"
```

Если этих сообщений нет, а ошибки есть — отказ приходит раньше, чем доходит до базы:
на стороне приложения или сети.

Признаки утечки соединений со стороны приложения в логах базы видны как неожиданно
большое число простаивающих сессий:

```logql
{namespace="dbaas", pod="<pod>"} | json | record_backend_type = "client backend"
```

## Возможные причины

| Причина | Признак |
|---|---|
| Исчерпание пула подключений | Мало активных транзакций при большом числе соединений |
| Слишком много клиентских соединений | Число реплик приложения выросло, лимит не пересмотрен |
| Неверная конфигурация пула | Соединения не переиспользуются, растут ступенями |
| Утечка соединений в приложении | Соединения не освобождаются после ошибок, число только растёт |
| Временная недоступность базы | Ошибки сопровождаются пропажей метрик |
| Ограничение `max_connections` | `cnpg_backends_total` у предела |

## Интерпретация

- **`cnpg_backends_total` у лимита + сообщения `too many clients`** — причина подтверждена.
- **Соединений много, транзакций мало** — утечка или неверный пул, проблема на стороне
  приложения, но подтверждается данными базы.
- **Ошибки есть, сообщений в логах базы нет** — отказ до базы, смотреть сеть и приложение.
- **Всё в норме, но ошибки повторяются** — данных для вывода недостаточно.

## Что рекомендуется пользователю

- Проверить, использует ли приложение пул соединений.
- Проверить настройки пула при пересмотре числа реплик приложения.
- Проверить, закрываются ли соединения при обработке ошибок.
- Проверить, освобождаются ли соединения после таймаутов.

**Увеличение `max_connections` — не решение.** Каждое соединение потребляет память, и рост
лимита на базе с ограниченной памятью приведёт к её исчерпанию и перезапуску. Это лечение
симптома, а не причины.

## Критерии передачи SRE

- `cnpg_backends_total` достиг `max_connections` или близок к нему.
- Причина не локализуется на стороне приложения.
- Требуется платформенное изменение параметров.

## Ограничения

- Список соединений с их источником и текстом запросов недоступен: метрики агрегированы.
- Причину утечки соединений в коде приложения база не покажет.
- Наличие большого числа соединений само по себе не доказывает проблему.
